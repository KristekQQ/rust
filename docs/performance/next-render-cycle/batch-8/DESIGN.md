# WebGL XR presentation prototype

Pinned public APIs, not private handle guesses: wgpu30.0.1 (local patch affects WebGPU adapter xrCompatible only), wgpu-core/hal/types30.0.1. `Device::as_hal<Gles>` -> `Device::context().webgl2_context()` exposes the renderer's real context. Public HAL `TextureInner::ExternalFramebuffer` wrapped by `Device::create_texture_from_hal` is the backend-supported external render target. The wrapper is frame-local, render-attachment only, never sampled/copied/destroyed as an owned XR FBO. Backend registration increments texture counters; HAL ExternalFramebuffer destruction does not delete the browser FBO. No HAL fork.

`shared-framebuffer` creates XRWebGLLayer on the existing renderer context. Renderer-owned per-eye sRGB color/depth targets preserve separate eye uniforms, depth, postprocessing and asymmetric size. One backend-controlled final color-only pass clears the layer and copies both eyes into their exact GL viewport/scissor rectangles. No raw JS framebuffer bindings on this route, no canvas present, no cross-context texSubImage2D. The final shader reproduces pinned GLES normal sRGB presentation math; sampling the sRGB eye texture decodes, then re-encodes once. XR alpha is opaque1. Single-sampled layer/context required. External target is never given depth/MRT attachments. State reset is backend-owned for every submitted command buffer.

Default `canvas-transfer` remains functional and unchanged. An unavailable capability probe falls back with an event; invalid actual AA/context or runtime import fails clearly, closes the session and preserves explicit retry via default. The shared renderer context is never deliberately lost during cleanup. A shared-context loss ends XR but cannot restore wgpu resources: caller must dispose/reinitialize the engine; tests cover fresh engine reentry. Private presentation-context loss leaves renderer alive.

W3C [opaque framebuffer rules](https://www.w3.org/TR/webxr/#opaque-framebuffer): do not inspect/change/delete opaque attachments; use the FBO only within its owning XR frame callback; compositor expects sRGB color. Public wgpu GLES ExternalFramebuffer binds but does not inspect/rebind attachments. Desktop simulator FBOs are ordinary FBOs; passing that test alone is not real opaque-FBO/device proof.

Opt-in `presentationDiagnostics` records bounded CPU histories and asynchronous valid EXT timer queries, separately from clean benchmarks. Two contexts remain separate timing domains on the original route. CPU texSubImage2D wall duration cannot identify complete GPU transfer cost. Whole-stereo application queries are separately sampled and not added to phase times. WebGPU owned-eye staging/final submit remain untouched.

Timing domains: the fallback's whole-stereo query is an **XR-context command interval**, not a guarantee that it brackets all commands in the separate renderer context. Cross-context flushing/scheduling can occur outside that interval. Full stereo CPU callback wall is available; complete cross-context stereo GPU time/compositor time remains unavailable. Shared route has one context, so its whole application query brackets its own submitted GL work, still including scheduling gaps. Phase samples are not additive; do not infer a transfer-only speedup from route-level FPS.

Device boundary: simulator `makeXRCompatible()` is a no-op. Real browsers may migrate/lose/restore a context when making it XR-compatible; wgpu resource restoration is not implemented here. The listener ends the session and requires engine reinitialization on shared-context loss. This remains a concrete reason to keep opt-in until physical-device acceptance. Simulator layer storage is ordinary RGBA8 plus an unused depth16 attachment; requested XR layer depth is false, renderer-owned depth remains32float. Real opaque attachment allocation is browser-owned/uninspected. No claim of physical framebuffer format inspection is made.

Pinned Three control audit (source-only, not a B8 benchmark): existing local r170 vendor SHA256`ce1fa418de16a19495a9f72495580e3015d7745c296d3ce0485897f902ddedfb`. WebXRManager makes its renderer GL context XR-compatible (`three.module.js:27378`), creates the legacy layer on that context (`:27395`), then assigns its current browser FBO through renderer-owned `setRenderTargetFramebuffer`/`setRenderTarget` (`:27808`, implementation`:31121`). This is the relevant same-context/renderer-owned-state technique; our implementation uses wgpu's public HAL import rather than copying Three's private render-target internals. Authored `rim-three/app.js:14` requests antialias=true, `:18` scale1; layer init forwards actual context AA/depth/stencil and alpha=true. Native B8 is AAfalse/depthfalse/alphaopaque, so no new matched Three XR timing/ranking is claimed. Future comparison must record actual runtime layer/foveation/eye sizes rather than infer them from authoring defaults.
